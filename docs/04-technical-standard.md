# 04 · 技术设计与工程规范

版本 v0.2 · Riot 公开实践参考 · 预研提案 · 未锁定正式引擎与 SDK

## 1. 规范依据与平台路线

工程方向参考 Riot 公开的服务器权威、网络体验和负载测试实践；代码格式、模块划分及检查阈值由本项目制定。当前可执行基线、实施顺序和验收见 [Riot 参考制作基线](11-riot-production-baseline.md)，来源见 [公开参考](07-public-references.md)。

微信目标是微信小游戏形态；如果后续还需要活动、客服等普通小程序页面，可另设入口，不把普通小程序直接等同于 3D 游戏运行环境。

建议优先预研 Unity/团结引擎路线：共享 C# 核心与 3D 资产，iOS 构建原生 App，微信端通过适配工具链构建小游戏。引擎手册提供了微信小游戏导入与部署流程，但不意味着本项目的网络库、资源加载和性能已兼容。[引擎官方部署说明](https://docs.unity.cn/cn/tuanjiemanual/Manual/UploadWeixinMiniGame.html)

TECH-001：G1 必须用实际支持的引擎/转换 SDK 版本完成双端真机验证，检查授权、包体、缓存、线程限制、网络传输和代码裁剪；锁定精确版本与依赖校验值。当前不写死未经测试的版本号。

已查看的 GitHub 地址 `wechat-miniprogram/minigame-unity-webgl-transform` 当前显示禁用，不能作为可用下载依赖。需从微信/引擎官方当前入口重新核对发行渠道。若路线未通过 G1，再评估 Cocos Creator 3D 等备选，形成 ADR，不同时维护两套战斗实现。

## 2. 架构与模块边界

客户端分层：

- `Game.Domain`：战斗、任务、计时、状态、配置模型；纯 C#，不依赖 Unity、平台 SDK 或 UI。
- `Game.Application`：房间流程、角色选择、游戏事件、展示数据组装。
- `Game.Presentation`：场景、模型、动画、音效、触控、UI、客户端预测表现。
- `Game.Infrastructure`：传输、缓存、资源加载、配置读取、遥测。
- `Game.Platform`：微信、iOS、编辑器适配，统一登录/支付/分享/生命周期接口。

服务端分为身份与账户、房间与战斗、配置与资源版本、订单与权益、遥测与管理功能。早期允许在一个服务部署中保持模块边界，不为样机拆出大量微服务。

战斗服务初步考虑 .NET 无图形运行并复用 `Game.Domain`；只有客户端负责渲染和动画。服务端使用平面角色碰撞、静态阻挡与固定更新，不依赖客户端 PhysX 结果。若必须使用引擎物理，需另评估专用服务器构建与成本。

持久化优先采用关系数据库保存账户、订单、权益与结算；缓存用于会话和房间索引。对象存储/CDN分发版本化资源。供应商和数据库产品待容量、预算与运维能力评审，不将具体云供应商作为玩法依赖。

## 3. 权威联机

TECH-010：正式房间由服务器裁决移动约束、碰撞、伤害、AI、掉落、任务、计时、救援和结算。客户端发送输入与意图，不发送可信的“已命中”“已通关”“余额”结果。

建议起点：服务器模拟 30 Hz，快照 10—15 Hz，客户端渲染按设备 30/60 FPS；G1 实测后定版。移动使用客户端预测与纠正，其他角色使用快照插值。命中受服务器裁决，初版不实现完整回滚物理。

网络初版优先评估 WSS/二进制协议，业务使用 HTTPS；两端通过同一传输抽象连接。高频输入合并、过期移动快照丢弃，可靠事件有序重放。WSS 的队头阻塞风险必须通过弱网测试；必要时改用经两端验证的传输方案，不能假设微信环境支持普通原生 UDP。

单房间分配单一战斗写入者。技术上不依赖房主设备，因此房主掉线不迁移战斗权威；房主角色仅控制开局前设置。房间设置冻结后不能在局中更改难度或收费英雄。

TECH-011：客户端时间仅用于表现；服务器维护活动计时与惩罚，在线不暂停。受击、任务提交、撤离与超时按同一服务器 tick 和事件序号排序，定义截止时刻为：服务器确认的撤离完成时间小于或等于截止时间有效。

## 4. 房间状态与错误处理

`Created → Preparing → Loading → Running → Settling → Closed`。

开局前未准备成员可被移除；加载超过初始建议 30 秒提示重试，正式计时不启动。`Running` 成员只能重连，首发不允许新账号替补。结算最长处理时间和重试预算通过服务配置提供。

重连鉴权包含短期令牌、账号、房间与玩家身份；服务器返回快照、最后确认输入序号、可靠事件序号、资源版本和剩余时间。客户端丢弃旧房间缓存；重连不能重复拾取、救援或发奖。

战斗进程异常终止时，不生成虚构通关结果：该局标记服务异常，退还本局正式消耗的道具并记录补偿流水。服务器故障恢复能力可后续增加；初版不承诺恢复每个战斗 tick。已持久化的合法结算不回滚。

## 5. 协议与接口规范

业务请求包含 `request_id`、`protocol_version`、身份凭据及必要业务参数；响应包含稳定错误码、服务器时间及追踪标识。错误码需区分身份过期、资源版本不符、房间已结束、物品已被拾取、请求过频和服务异常。

战斗输入包含 `room_id`、`player_id`、`sequence`、客户端采样 tick、移动向量、按键位和候选目标。服务端校验身份、序号窗口、频率、移动幅度、技能冷却及目标合法性。客户端采样 tick 不能修改服务器倒计时。

快照包含 `server_tick`、可靠事件序号、实体状态、任务状态、倒计时、退出状态和已确认输入序号。协议采用明确字段 ID 与兼容策略；新增可选字段不破坏旧解码，破坏性变更提升协议主版本。

逻辑 API 提案：登录、刷新会话、创建/加入/离开房间、准备、重连、查询结算、创建订单、校验平台交易、恢复权益。确切路径与序列化格式在 G1 形成接口契约后冻结。

正式请求使用服务端验证的平台身份；不能把昵称、头像或客户端传来的平台 ID 当作认证。跨端账号绑定必须同时验证两侧归属；相同昵称不自动合并，存档冲突提供确定策略。

## 6. 账户、奖励与支付

TECH-020：账户余额、进度、库存、订单、权益与奖励仅由服务器写入。客户端可以缓存展示，不得直接覆盖服务端存档。

结算唯一键建议 `room_id + player_id + settlement_version`；道具消耗有库存流水。一次结算中，资格判断、奖励入账和幂等记录在同一事务完成。客户端断线后可查询既有结果，不重新生成奖励。

订单状态：`Created → PendingVerification → Granted`，取消、失败、退款和撤销为独立受控分支。平台交易 ID 加唯一约束；校验商品、数量、归属、环境、交易真实性后授予权益。

发货任务支持重试和对账；支付成功但网络中断时从服务端恢复，不依赖前端成功弹窗。退款先更新权益账本；局中战斗配置冻结，受影响英雄在下一局禁用；消耗品退款/负余额策略须在上线前评审并公开适用规则。

iOS 数字英雄、道具和装扮默认按 Apple 的应用内购买规则设计；具体地区例外和支付入口需逐发行地区核对。微信支付适配独立处理，未核实支持范围前不承诺与 iOS 使用同一收款入口。[Apple 审核指南 3.1.1](https://developer.apple.com/app-store/review/guidelines/#in-app-purchase)

## 7. 配置与版本

策划源数据可使用表格，构建时转换为强类型 JSON/二进制配置。字段有范围、引用和唯一 ID 校验。正式战斗读取固定配置版本；在线更新只能用于下一局，不能让同房玩家采用不同规则。

资源清单包含包版本、哈希、依赖、大小与回退版本；下载先验证再启用，断网不能产生半更新状态。代码更新通过平台允许的发布机制；禁止以资源热更新绕过平台对可执行代码的审核要求。

## 8. 工程与代码规范

TECH-030：源码、策划配置和文本进入版本控制；大二进制与美术源文件使用大文件存储或资产管理，保留源文件和导出物关联。生成缓存、证书、密钥、真实账号数据不入库。

C# 类型与公开成员采用 PascalCase，局部变量采用 camelCase；私有字段统一 `_camelCase`；资源与配置 ID 使用稳定小写下划线。命名描述业务用途，避免 `Manager1`、`TempData` 等模糊名称。

业务代码依赖单向；UI 不直接写数据库；平台 SDK 不进入领域层。关键战斗路径避免每帧分配、反射和无界集合。异步任务必须可取消、异常可追踪；订阅事件、对象池与资源引用有清晰生命周期。

所有提交需关联需求/缺陷 ID；合并前评审。MUST 无编译错误、无阻断级静态分析问题、无泄露密钥、核心规则测试通过。SHOULD 单函数圈复杂度不超过 15；超限说明算法原因和验证方法，不机械拆函数掩盖复杂度。

静态分析根据选定语言采用语法、类型、格式及依赖检查，并纳入 CI。当前 JavaScript 原型保留既有运行方式；正式 C# 工程的规则不强行套在 JavaScript 上。依赖锁定并核验安全问题和许可证；验证结果仅表示通过本项目门禁。

测试优先覆盖计时边界、结算幂等、任务进度、救援、协议验证、库存扣减和退款权益，不以大量重复实现的测试提高表面覆盖率。

## 9. 日志、容量与运维

日志字段包含时间、环境、版本、服务、追踪 ID、房间 ID 和匿名玩家标识；禁止输出登录令牌、支付凭据、真实身份信息。错误附稳定错误码，战斗详细日志按问题采样，避免每 tick 全量输出。

容量按目标并发计算：战斗房间数约等于并发玩家数/实际平均房间人数，不能固定假设每房四人。测量单房 CPU、内存、带宽、网络往返延迟和尾部 tick 耗时，再推算节点与成本；目标并发当前待定。

发布需有测试/预发布/生产隔离、配置审计、资源回退和维护开关。崩溃、结算失败、重复发奖、支付对账差异与加载失败有告警。处置负责人和阈值在首发前填写，不留作无人响应的仪表盘。

## v0.4.0 原型实施状态（2026-10-03）
